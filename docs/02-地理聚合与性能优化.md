# 地理聚合与性能优化

> P2 产物。真实指标由 `scripts/benchmark_aggregation.py` 生成，证据见 `artifacts/bench/aggregation.json` 与 `artifacts/bench/explain.txt`。

## 两级聚合

渲染聚合解决“10w 点不下发、不直接画”的问题。接口层按 `bbox + zoom + filters` 返回网格簇，zoom 到网格尺寸的映射使用施工书 §4.4 冻结值。

业务批次解决“哪些表单交给同一片区处理”的问题。批次聚合不复用渲染簇，因为渲染簇会随视野和 zoom 改变，而业务批次必须稳定、可审计、有容量约束。

## 距离口径

候选排序使用等距圆柱近似：

```text
x = (lng2 - lng1) * cos(avgLat) * 111320
y = (lat2 - lat1) * 110540
```

最终合批使用 Haversine 校验，默认容量 50、最大半径 3000m，且先按 `city_code` 分区，禁止跨城市合批。

## 算法对比

| 算法 | 用途 | 结论 |
|---|---|---|
| 全扫描 + 向量化网格聚合 | 基线 | 每次查询都扫候选全集，用来证明正确性和作为性能下限。 |
| 预建网格索引 + 向量化聚合 | 渲染主路径 | 先按 bbox 命中网格候选，再做精确 bbox/filter，适合 10w 级动态过滤。 |
| cKDTree 候选 + 向量化聚合 | 对照与规模化建议 | 在城市级 bbox 候选率高时不一定更快；保留它作为规模化和局部查询对照。 |
| 暴力/网格候选/cKDTree 贪心批次 | 业务批次 | 三者不要求逐位一致，只要求唯一分配、容量、半径这些业务不变量成立。 |

## Benchmark 口径

`aggregation.json` 中 `n=99304`，来自 100000 条合成表单去除 500 条越界坐标与 200 条非法状态后得到；其中有 4 条样本同时命中两类异常，所以不是简单相减。

批次构建工作负载固定使用上海 published 的前 2000 条，模拟“单城单日待处理工作集”。批次半径语义是“成员距 seed 表单 ≤ 3000m”，不是两两距离都 ≤ 3000m，也不是成员距质心 ≤ 3000m。

在 2000 条小样本上，网格候选版本可能因为 Python 字典/集合维护成本慢于暴力或 cKDTree；这里保留它不是为了宣称小数据最快，而是为了展示“先缩小候选，再做距离排序”的业务批次路径。性能结论以 `aggregation.json` 的实测数据为准。

payload 工作负载真实测量 JSON 序列化耗时和字节数；全量点与聚合簇的 payload 对比是前端渲染压力的直接证据。

EXPLAIN 证据同时保留优化器自然选择与 `FORCE INDEX(ix_forms_tenant_status_type_city_lng_lat)` 对照。P4 已将 P0 合成数据导入 MySQL，`forms` 现有 97354 条可消费记录，优化器自然选择命中冻结复合索引。

## 证据

- `artifacts/bench/aggregation.json`：三类工作负载，字段包括 `workload,algorithm,n,p50_ms,p95_ms,total_ms,payload_bytes,features_count,peak_memory_mb,correctness_passed`。
- `artifacts/bench/explain.txt`：forms 多维过滤查询的 MySQL EXPLAIN，验证复合索引路径。
- `backend/tests/test_aggregation.py`：聚合一致性与批次不变量单测。
