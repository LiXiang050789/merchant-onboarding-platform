# 需求理解与设计说明

## 总体理解

这道全栈作业不是让候选人把技术标签全部堆上去，而是考察能否把一个 B 端入驻流程拆成可解释、可验证、可维护的系统。题目开头强调“权限和数据要素准确性”，所以我把租户隔离、状态机、幂等、审计、统计口径放在第一优先级；地图、RAG、Spark 都围绕这条业务主线服务。

## 题目逐条拆解

| 原题要求 | 我的业务理解 | 对应设计 | 证据 |
|---|---|---|---|
| 企业方提交申请入驻订单/表单 | 表单是业务事实入口，必须能说明是谁提交、属于哪个租户、当前处于什么状态 | 四类统一 `forms` 模型，`created_by/tenant_id/status/idempotency_key` 作为核心字段 | `backend/app/models.py`, `backend/app/repositories.py` |

| 商户信息/房源/商品/报表流程 | 四类表单字段不同，但状态流转和批处理框架一致 | `REQUIRED_BY_TYPE` 校验，四个 pipeline stage，checkpoint 记录最后处理点 | `backend/app/schemas.py`, `backend/app/batch_pipeline.py` |
| 多维表单数据处理/查询过滤器 | 查询要同时考虑租户、角色、城市、状态、类型、行业 | Repository 层统一 tenant/region scope，接口支持 city/status/form_type/industry | `backend/tests/test_forms.py` |

## 为什么这样取舍

### 不引入 C++

题目列了 C++，但当前瓶颈主要在数据库查询、payload 大小、前端渲染和流程正确性。用 Python/Numpy/SQL 已经能把 10w 规模、批次半径、缓存和测试证据讲清楚；为了少量潜在收益引入候选人不熟悉的 C++，会降低答辩可解释性。

### 不用 PostGIS 作为第一版

PostGIS 对真实空间检索很强，但一周作业里会增加环境、迁移和 SQL 空间函数解释成本。本项目用 bbox/zoom 网格聚合和 Haversine 终判覆盖题目规模，并在文档里说明生产可升级路径。

### RAG 不是主线

知识文档题首先要求 CRUD，所以 Mongo 版本、软删、回滚和并发写才是主线。RAG 作为技术栈点名的加分项，只读取已有知识文档并输出引用；无 key 或网络失败时降级 retrieval-only，避免演示链路被外部服务绑死。

### 实时能力的边界

当前 WebSocket 是单实例内存事件队列，适合本地演示和作业证明。多实例生产需要 Redis PubSub、消息队列或专门 worker 锁；这个限制已写入 README 和批处理文档，不把 demo 能力包装成生产集群能力。

## 面试开场口径

我会先说：这题我理解成一个商户入驻后台，而不是单纯地图 demo。我的优先级是租户权限和数据准确性，然后才是 10w 聚合、批处理和前端缓存。地图聚合只解决“看得快”，业务批次解决“处理得稳”；成功率只读事件表，撤回、重试、迟到事件都有明确口径。RAG、Spark 和预测是围绕这条主线补充的加分项，不抢主线。
