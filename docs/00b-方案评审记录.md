# 方案评审记录（施工书 v1 → v2）

> 记录一次独立方案评审的意见与逐条裁定，体现设计决策过程。
> 评审方式：将施工书 v1 与原始题目交给一个独立的大模型（Codex/GPT）做对抗性审查（角色设定为"资深架构师 + 技术面试官"），要求"找茬优先"。
> 裁定原则：**采纳看两点——是否更贴题目、是否更利于候选人现场答辩**；不因"更高级"而采纳。

---

## 一、采纳的修改（10 项）

| # | 评审意见 | 裁定 | 理由 |
|---|---------|------|------|
| 1 | 补「权限与数据准确性」一级设计：RBAC、tenant 隔离、字段/坐标校验、审计事件、非法状态流转测试 | **采纳** | 题目前言的显性要求（"权限和数据要素的准确性是重点"），v1 只映射了 bullet 点、漏了前言。且该能力与实现者实习经历（JWT/RBAC/状态机非法流转测试）直接对应，可答辩 |
| 2 | 聚合主路径改为可解释性优先：渲染用网格分桶，批次用"网格候选+距离排序+容量约束"，KDTree 降为基准对照 | **采纳** | 一周时间盒 + 面试以"讲得清"为准；H3 的层级汇总优势在本项目规模下收益不抵解释成本；KDTree 保留在基准对比与大规模建议中 |
| 3 | 基准从 4 算法减为 3（暴力/网格/KDTree） | **采纳** | H3 移出代码进选型对比文档，避免实现面铺太宽 |
| 4 | Spark 从"双主引擎"降为"可运行 demo + 同构验证" | **采纳** | 10w 规模下单机更优是事实，诚实框架（"Spark 是规模化路径"）比硬凑更有说服力 |
| 5 | 缓存五层砍到三层，砍 IndexedDB | **采纳** | 题目仅要求"缓存与网络请求"，非离线优先；ETag + Redis + SWR 已闭环。IndexedDB 降级为跨端文档中的离线策略 |
| 6 | WebSocket 收窄为状态增量 + 提供轮询降级 | **采纳** | 避免被追问"为什么不用轮询"时无准备；收窄到一个频道、少量事件类型 |
| 7 | 知识文档补并发语义：乐观锁（If-Match）、回滚=从历史版本创建新版本、软删可见性 | **采纳** | 这些细节是追问防线的护城河；回滚不覆盖历史是专业做法 |
| 8 | 幂等键具体化：客户端 UUID + 服务端唯一索引 `(tenant_id, idempotency_key)`；事件模型细化为 5 类 | **采纳** | 落地精确，直接支撑三口径 SQL |
| 9 | 表单模型统一为 `forms` 主表 + 类型判别 + 扩展字段 | **采纳（加物化列）** | 单表支撑聚合/过滤/统计；常用过滤字段（城市/行业/状态/经纬度/时间）物化为真实列以支撑索引与 EXPLAIN 证据 |
| 10 | 建立「需求覆盖矩阵」：题目每句 → 证据 | **采纳** | 防止"跑偏"质疑，P1 建骨架、P7 完成 |

## 二、部分采纳（1 项）

| # | 评审意见 | 裁定 | 理由 |
|---|---------|------|------|
| 11 | 砍掉真实 DeepSeek 调用，RAG 保留接口设计与 mock | **部分采纳** | RAG 是题目 backend 技术栈点名的能力，非偏题；保留为**限时加分项**（真实调用 + 问答记录），排期告急时第一顺位降级为设计+mock。同时按评审意见调整定位：知识文档先做扎实 CRUD/版本/检索，RAG 作为独立问答接口而非"知识文档的必然延伸" |

## 三、未采纳（0 项否决，1 项调整）

无整条否决。唯一的表述调整：评审认为"表单改知识文档不必然要 RAG"——结论正确，故 RAG 的叙事定位从"文档存储的延伸功能"改为"技术栈点名能力的独立展示"。

## 四、评审未覆盖、本记录补充的点

- **MVVM 是显性要求**：施工书中前端分层（View/ViewModel/Model）必须清晰可见于目录结构与代码，不能在"数据平台"叙事中被弱化。
- **"会 js 优先"（JD）**：前端质量仍是评分项，P5 克制但不将就。

## 五、结论

v1 → v2 的核心收益：**从"技术展示最大化"转为"答辩可控性最大化"**。
判据统一为一句：*这个设计，候选人在技术面被追问三层时还能答得住吗？*
