# 系统架构设计

## 目标

本项目围绕商户入驻表单构建一条可演示、可追问、可验证的 B 端 SaaS 主线：

企业提交入驻表单 → 按地理坐标聚合 → 构建批处理批次 → 四类表单管线处理 → 成功率与报表统计 → 知识文档 CRUD/RAG。

优先级是权限、数据准确性、查询效率和证据链，而不是华丽 UI。

## 后端域

- 权限域：JWT HS256、access/refresh、RBAC、tenant 隔离。
- 表单域：四类表单 schema、状态机、审计事件、多维过滤器。
- 聚合域：网格渲染聚合、批次贪心聚合、benchmark 对拍。
- 统计域：6 类 submission event、三口径成功率、迟到事件容忍、Redis 窗口缓存。
- 批处理域：build/run、checkpoint、DLQ、幂等重跑、四类处理管线。
- 文档域：Mongo CRUD、版本、软删、回滚、jieba tokens 检索。
- 扩展层：Spark 同构、RAG demo、报表趋势预测。

## 前端 MVVM

`frontend/src/features/*` 下每个功能都有 `model / view-model / view`：

- `model`：API 类型、请求、query key。
- `view-model`：TanStack Query、筛选状态、mutation。
- `view`：只负责渲染和交互绑定。

这让候选人面试时能解释“为什么这是 MVVM”，而不是只在文档里写模式名。

## 数据准确性

- 所有业务查询强制 tenant scope；跨租户资源返回 404。
- operator 叠加 region scope；merchant 不能驱动后台状态流转。
- 表单创建使用 `Idempotency-Key` 去重。
- 文档更新使用 `If-Match` 乐观锁；回滚创建新版本，不覆盖历史。
- 统计口径基于事件表重算，测试覆盖重复、乱序迟到、重试成功和最终态。

## 性能路径

- 地图不下发 10w 点，只下发 bbox/zoom 聚合后的 GeoJSON。
- clusters 支持 Redis 缓存、ETag/304 和 TanStack Query 缓存。
- 批次构建先按 tenant/city 分区，再做半径和容量约束。
- Spark 同构用于证明可扩展路径；本地 10w 数据 Python 更快，文档中诚实说明。

## Why Not

- 不写 C++：热点主要在 IO、查询、payload 和前端渲染；Python/Numpy/SQL 已能解释清楚。
- 不上 PostGIS：一周作业里引入空间数据库会增加运维和答辩负担；当前城市级 bbox/网格足够。
- 不上 ES/Atlas Search：本地环境和中文检索成本过高；jieba tokens + Mongo multikey 更可控。
- 不把 RAG 绑死在 CRUD 主线：题目明确要求 CRUD，RAG 是技术栈点名的加分项。
