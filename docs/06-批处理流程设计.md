# 批处理流程设计

> P4/P9/P15 产物。代码证据见 `backend/app/batch_pipeline.py`、`backend/app/dlq_worker.py`；测试证据见 `artifacts/test/p4.xml`、`artifacts/test/p9.xml` 与 `artifacts/test/p15.xml`。

## 调度边界

批次构建只消费 `validated` 表单，并在 SQL 层强制 tenant 作用域。普通企业账号不能构建或运行批次；管理员可全局操作，区域运营只能操作自己 `region_code` 对应城市。

构建接口：

```text
POST /api/v1/batches/build
```

输入包含 `city/form_type/capacity/radius_m`。服务端按 `city_code` 分组后调用 P2 的网格候选贪心算法，写入：

- `batches`
- `batch_items`
- `forms.batch_id`
- `forms.status = batched`

## 四类管线

运行接口：

```text
POST /api/v1/batches/{id}/run -> 202 Accepted
```

四类表单映射到四个可观测 stage：

| form_type | stage |
|---|---|
| `merchant_info` | `merchant_info_pipeline` |
| `property` | `property_pipeline` |
| `product` | `product_pipeline` |
| `report` | `report_pipeline` |

每条记录运行成功后写 `batch_checkpoints(batch_id, stage, last_form_id)`，并把表单推进到 `published`。checkpoint 是每个 stage 最后一次成功的留痕证据，不是逐条完成清单，也不作为读取游标；续跑靠表单状态跳过，不依赖 checkpoint 恢复位置。重复运行已完成批次直接返回 completed，不重复写 `business_published` 事件。若批次尚未开始（`created`），创建者可通过撤回端点把 `batched` 表单移出批次；批次为空时置为 `canceled`。

## 异步运行与实时进度

P9 后运行接口只负责接收命令：校验权限与批次状态后把批次置为 `processing`，立即返回 `202 Accepted`，实际管线在 FastAPI background task 中继续执行。后台每处理 10 条或到达终点发布 `batch.progress`，完成后发布 `batch.status_changed`；批次页通过 WebSocket/轮询事件更新进度条。

admin 的实时通道为全局订阅（与 REST 全局视角一致），因此 admin 运行非本租户批次也能收到 `batch.progress` 与终态事件；普通租户账号事件仍严格按租户隔离。

测试语义也随之调整：不再要求 run 响应体同步给出 completed，而是先断言 `202 + processing`，再轮询数据库终态、checkpoint、DLQ 与幂等事件。这是接口语义升级，不是降低断言。

## DLQ 与重试

管线失败时：

- 当前表单标记为 `failed`
- `retry_count += 1`
- 写入 `dlq_items`，`state=pending`；次数已达 3 则直接 `exhausted`
- `next_retry_at = now + 2^min(retry_count,6) minutes`（该字段在 exhausted 状态不再触发调度）
- 批次标记为 `failed`

FastAPI lifespan 同时启动 DLQ worker，`DLQ_RETRY_INTERVAL_SECONDS` 默认 30 秒，生产可配置。每轮按 `next_retry_at, id` 升序选取最多 20 条 `pending AND next_retry_at<=now AND retry_count<3` 的记录，逐条事务提交；一条异常回滚该条并记异常日志，不影响后续条目。单条正常处理记录 id/state/retry_count 日志；状态事件在提交后发送。

重试复用管线校验、故障注入、业务事件去重与 checkpoint 写入：成功后表单 `published`，DLQ `resolved`，发 `form.status_changed`。失败后表单保持 `failed`，表单与 DLQ 的 retry_count 同步增加；次数小于 3 时按 `now+2^retry_count` 分钟再次调度，达到 3 时置 `exhausted`，不再自动消费。因此初次失败 count=1 后等 2 分钟，第二次失败 count=2 后等 4 分钟，第三次失败即终止，不再安排 8 分钟自动重试。这个预算包含初次管线失败，不是初次失败之外再重试三次。

表单已发布、已撤回或不存在时，DLQ 直接置 `resolved`，不补写重复业务事件。手动重跑已用完预算时，旧 pending 条目也会收敛为 exhausted。已有库通过 `scripts/load_seed.py::ensure_v6_schema` 幂等增加带索引的 state 字段；旧次数已达 3 的 pending 条目迁移为 exhausted。

每条处理后检查所属批次：仅当全部成员已 `published/withdrawn`，或 `failed AND retry_count>=3`，才收敛批次；没有 failed 成员则 `completed`，否则 `failed`，状态变化发 `batch.status_changed`。worker 只消费 DLQ，不自动执行 fail-fast 留下的其它 batched 成员；这些成员仍由重新运行同一批次推进。已有 `published/withdrawn` 记录会跳过，失败记录在 `retry_count<3` 时可继续处理。单实例为当前部署前提；DLQ/form 行锁不代表已解决多进程 worker 与手动整批运行的全部并发问题，多实例部署需统一任务领取与批次调度锁。

当前实现采用整批 fail-fast：遇到第一条失败记录即标记批次 `failed` 并写 DLQ；修复后重跑同一批次，已发布记录跳过，未完成记录继续推进。测试里使用 `payload.force_dlq_stage` 作为故障注入钩子，仅用于证明 DLQ 与续跑语义。
