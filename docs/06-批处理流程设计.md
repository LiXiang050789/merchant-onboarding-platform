# 批处理流程设计

> P4 产物。代码证据见 `backend/app/batch_pipeline.py`、`backend/tests/test_batch_pipeline.py`，测试证据见 `artifacts/test/p4.xml`。

## 调度边界

批次构建只消费 `validated` 表单，并在 SQL 层强制 tenant 作用域。普通企业账号不能构建或运行批次；管理员可全局操作，区域运营只能操作自己 `region_code` 对应城市。

构建接口：

```text
POST /api/v1/batches/build
```

输入包含 `city/form_type/capacity/radius_m`。服务端按 `city_code` 分组后调用 P2 的网格候选贪心算法，写入：

- `batches`
- `batch_items`
- `forms.batch_id`
- `forms.status = batched`

## 四类管线

运行接口：

```text
POST /api/v1/batches/{id}/run
```

四类表单映射到四个可观测 stage：

| form_type | stage |
|---|---|
| `merchant_info` | `merchant_info_pipeline` |
| `property` | `property_pipeline` |
| `product` | `product_pipeline` |
| `report` | `report_pipeline` |

每条记录运行成功后写 `batch_checkpoints(batch_id, stage, last_form_id)`，并把表单推进到 `published`。重复运行已完成批次直接返回 completed，不重复写 `business_published` 事件。

## DLQ 与重试

管线失败时：

- 当前表单标记为 `failed`
- `retry_count += 1`
- 写入 `dlq_items`
- `next_retry_at = now + 2^retry_count minutes`
- 批次标记为 `failed`

修复失败原因后可重新运行同一批次；已 `published` 的记录跳过，失败记录在 `retry_count < 3` 时继续处理。这保证批处理重跑是幂等的，且 checkpoint 能证明哪些 stage 已经推进。

当前实现采用整批 fail-fast：遇到第一条失败记录即标记批次 `failed` 并写 DLQ；修复后重跑同一批次，已发布记录跳过，未完成记录继续推进。测试里使用 `payload.force_dlq_stage` 作为故障注入钩子，仅用于证明 DLQ 与续跑语义。
